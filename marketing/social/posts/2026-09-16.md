### LinkedIn
Two prompts that look identical in a text box, and one of them quietly returns worse answers.

The difference is a single trailing space.

Tokenizers hand the leading space to the word that follows it. Under cl100k_base, "hello" is token 15339 and " hello" is 24748: two unrelated rows of the embedding table, not neighbours.

So "The capital of France is" ends on the token " is", and the natural next token is " Paris". Common, well trained, exactly what the model saw a million times in pretraining.

Add one space at the end and you have supplied that space yourself. Now the model has to produce "Paris" with no leading space, a rarer token in a context where nearly all of its training saw the other form.

Same string to you. A different row of the embedding table to the model.

Nothing errors. Nothing gets logged. The output just drifts slightly worse, and the usual reaction is to rewrite the wording of the prompt.

It turns up most in prompts assembled in code: an f-string, a join, a few-shot template that ends with a colon and a space.

The fix is one line. Strip trailing whitespace where the prompt is assembled, and let the model produce the space as part of its first token. Then assert it in a test, because the next person editing that template will not know.

What is the smallest thing that has ever cost you a quality regression?

### LinkedIn first comment
Tabs carry the same effect: "\treturn" is a single entry in Llama 3's vocabulary, so a tab-indented file and a space-indented file of identical code do not cost the same number of tokens.

## Slot 6 · 15:00 · The code · X
**Course:** Databases in Depth · ch 29 (PocketDB: The WAL) · **Mentions product:** no

### X
PocketDB's crash safety is one ordering rule, not a library. put() writes to the log with no fsync. commit() writes a COMMIT record, then fsyncs. The line to stare at: durability happens on that one fsync call, not on every write.

### Reply
none

```java
// image: render with ray.so
void put(long txId, byte[] key, byte[] val) throws IOException {
    wal.append(Wal.PUT, txId, encode(key, val));  // log it, no fsync yet
    tree.put(key, val);                           // apply to cached pages
}

void commit(long txId) throws IOException {
    wal.append(Wal.COMMIT, txId, EMPTY);          // the commit record
    wal.sync();                                   // durability happens HERE
}
```
