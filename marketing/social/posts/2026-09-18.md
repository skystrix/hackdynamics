### LinkedIn
An HNSW index at M = 16 finds 79% of the true top 10 neighbours on random vectors. Same graph, same parameters, on embeddings that cluster the way real text does: 93%, touching a quarter as much of the corpus to get there.

Nothing about the index changed. The data did, and that gap is the real answer to an interview question: what would you tune first?

HNSW searches a graph, not raw vectors, and it has exactly two knobs that are easy to mix up.

M is how many links each node keeps. It's set at build time: more links, better recall, but changing it means a full rebuild.

ef_search is the beam width at query time, how many candidates the search keeps alive while it hunts for the one node that bridges into the region holding the true neighbours. Raise it and recall climbs immediately. No rebuild. It takes effect on the very next query.

So the order in production is fixed. Measure recall against brute force first. Then raise ef_search, because it's free. If recall stalls, climbing from 0.85 to 0.93 and then sitting flat past ef = 80, that plateau is not a search problem anymore: the beam can only explore edges that already exist. At that point the fix is ef_construction or M, and a rebuild.

Mixing the two up is the most common HNSW mistake in production: turning the free knob well past where it can still help, on a graph that needed rebuilding an hour ago.

### LinkedIn first comment
One more thing that trips people in production: deleting a vector doesn't remove it from the graph. hnswlib marks it deleted and filters it from results, but the node stays in the graph as a routing point, so recall drifts down and latency creeps up with nothing in the logs, until you rebuild.
